# Known issues in Slotlock 0.2.0

What users of 0.2.0, and of the 0.1 releases before it, need to know until 0.3.0 is published, and
the text the maintainer publishes for them: the v0.2.0 release notes, a pinned issue and two
security advisories. The README's [Known issues in 0.2.0](https://github.com/PILOTAAI/slotlock#known-issues-in-020)
section and the site's `/docs/known-issues/` page say the same. Deprecating the old versions on npm
and in the MCP Registry is in [deprecations.md](deprecations.md).

The defects were found by the 24 October 2026 readiness audit, which reproduced each one against the
published `slotlock@0.2.0` on PostgreSQL 16.

## The notice

Use this text, unchanged, in the release notes and the pinned issue.

> **Known issues: upgrade to 0.3.0 when it is published.** Slotlock 0.2.0 can occupy less time
> than a recurring event was written with, so another booking can take the rest: around
> daylight-saving changes, in any time zone that has them, and at the end of some series. The
> library and `slotlock serve` are affected alike:
>
> - A recurring event whose first occurrence spans a daylight-saving change gets that occurrence an
>   hour short: in spring, an hour of the written time is free to book.
> - Recurring events written through the store (the agent tools and the application API) lose the
>   repeated hour of an autumn change: times in it move an hour early, and a series whose first
>   occurrence spans it can store no occurrences, so all of its time is free.
> - A stored recurring series cannot cancel or move an occurrence that falls in the skipped hour of
>   a spring change; the time it was moved to stays free.
> - An occurrence that starts in the skipped hour and lasts longer than the skipped hour is cut
>   short: a 75-minute occurrence occupies 15 minutes.
> - A timed recurring series with a date-only `UNTIL` ends at midnight UTC, so it can lose its last
>   day.
>
> 0.1.0, 0.1.1 and 0.2.0 also pin zod 4.6.5 exactly, which has a high advisory
> ([GHSA-mrhx-c7xc-m3w5](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5)), so `npm audit` reports
> it with no fix available. Until 0.3.0, add `"overrides": {"zod": "4.6.7"}` to your application's
> `package.json` and run `npm install`.
>
> Details: https://github.com/PILOTAAI/slotlock#known-issues-in-020

The override was checked on 24 October 2026 with npm 11.17.0: in a project that installs
`slotlock@0.2.0`, `npm ls zod` shows `zod@4.6.7 overridden` and `npm audit --omit=dev` reports no
vulnerability, against two high ones without it.

## The v0.2.0 release notes

Put the notice at the top of the release's notes, keeping the rest:

```sh
gh release view v0.2.0 --repo PILOTAAI/slotlock --json body --jq .body > notes.md
# Paste the notice above, as a quote, at the top of notes.md.
gh release edit v0.2.0 --repo PILOTAAI/slotlock --notes-file notes.md
```

Re-running the v0.2.0 Release workflow would rewrite the notes from CHANGELOG.md; do not re-run it.

## The pinned issue

Title: "0.2.0 can double-book around daylight-saving changes: upgrade to 0.3.0". Body: the notice,
then "This issue stays open until 0.3.0 is on npm."

```sh
gh issue create --repo PILOTAAI/slotlock --title "0.2.0 can double-book around daylight-saving changes: upgrade to 0.3.0" --body-file notice.md
gh issue pin <number> --repo PILOTAAI/slotlock
```

## Security advisory drafts

Repository **Security > Advisories > New draft security advisory**, one for each. Fill in the
patched version once 0.3.0 is on npm, then publish: SECURITY.md promises that a security release
names the lowest safe version. The suggested scores use the CVSS 3.1 base equations and weights
(first.org/cvss/v3.1/specification-document, read 24 October 2026); the maintainer sets the final
severity.

### 1. Slotlock pins zod 4.6.5, which can exhaust memory on oversized input

- Ecosystem: npm. Package: `slotlock`.
- Affected versions: `<= 0.2.0`
- Patched versions: `0.3.0`
- Severity: Moderate, CVSS 3.1 6.5 (`CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:N/A:H`). The upstream
  advisory is High (7.5) because zod parses unauthenticated input there; Slotlock parses tool and
  REST input only after it has authenticated the caller.
- Weakness: CWE-770, allocation of resources without limits.
- Description: Slotlock 0.1.0 to 0.2.0 depend on exactly `zod@4.6.5`, which GHSA-mrhx-c7xc-m3w5
  covers: validating an oversized array collects an issue for every failing element with no cap.
  Any caller with an API key or the server token can send such an array to a tool or REST route.
  The request body limit (256 KiB by default, 1 MiB at most) bounds the cost. At the default limit
  the audit measured 93 ms and a heap of up to 162 MB for one such call, against 21 ms and 15 MB
  with zod 4.6.7; at 1 MiB, 608 MB, and a process limited to a 256 MB heap ran out of memory.
  Workaround: add `"overrides": {"zod": "4.6.7"}` to the application's `package.json` and run
  `npm install`. Upgrade to 0.3.0, which depends on a fixed zod.

### 2. Slotlock can accept double bookings around daylight-saving changes and series ends

- Ecosystem: npm. Package: `slotlock`.
- Affected versions: `<= 0.2.0` (reproduced on 0.2.0; the 0.1 releases expand series with older
  code that was not tested separately, and are unsupported)
- Patched versions: `0.3.0`
- Severity: Moderate, CVSS 3.1 6.5 (`CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:H/A:N`): refusing
  overlapping bookings is the guarantee Slotlock exists to give.
- Weakness: CWE-682, incorrect calculation.
- Description: when Slotlock expands a recurring event, it can occupy less time than the event was
  written with, so the time left out can be booked by someone else: around daylight-saving changes,
  and on the last day of a timed series with a date-only `UNTIL`. The cases are the five in the
  notice above. Reproduced on 0.2.0 with Europe/Berlin and Europe/London series around the changes
  of 28 March 2027 and 25 October 2026, and a Europe/Berlin daily series ending 6 January 2027.
  There is no configuration that avoids them; upgrade to 0.3.0.
